# 採用LPスキル（saiyo-lp）

## このスキルの考え方
- AIに「いい感じに」と判断させると、どの会社でも同じ見た目になる。**判断材料（OFFER.md・DESIGN.md・禁止リスト・型）を先にファイルにして、そこから選ばせる**
- 成果を決めるのは見た目ではなく構造。**ファーストビューの4点セット**と**求職者が知りたい情報を全部出すこと**を最優先にする
- 手戻りが高い工程（画像生成・実装）の前には必ずユーザーの承認を取る
- 作ったエージェントに採点させない。**採点は別のサブエージェント**
- ダメ出しは `rules.md` に追記し、次のLPから最初に読む。1本磨いてから複製する

## 作業フォルダ
案件ごとに `<リポジトリ>/saiyo-lp/<会社スラッグ>/` を作る（例 `saiyo-lp/hado-kensetsu/`）。

```
<slug>/
├── OFFER.md          会社・職種・ターゲット・訴求・数字（ヒアリング結果）
├── DESIGN.md         色・書体・余白・Signature Element・禁止リスト
├── references/       参考画像。ファイル名で「何を借りるか」を示す（hero-01.png / type-01.png / photo-01.png）
├── mocks/            ファーストビュー案（gpt-image-2）
├── images/           本番で使う写真（クライアント支給 or 生成）
├── index.html        完成品（1ファイル・CSS内包）
├── shots/            スクショ（sp.png / pc.png）
└── review.md         採点結果
```

## 手順

### 1. ヒアリング → OFFER.md
`references/hearing.md` の項目を聞く。**1回に3問まで**、答えを踏まえて次を聞く。分からない項目は「おまかせ」で飛ばしてよいが、**数字（給与・休日・平均年齢・実績など）は推測で埋めない**。未確定は `【要確認】` と書く。
最低限そろえるもの：会社名／職種・雇用形態／勤務地／給与（下限〜上限）／ターゲット（年齢・今の状況・一番の悩み）／採用の背景／競合との違い／CTA（LINE登録・面談予約のURL）／流入元（Meta広告などの動画広告か、検索か）。
動画広告からの流入なら、**広告と同じフック（職種名・数字）をファーストビューで繰り返す**。

### 2. DESIGN.md と禁止リスト
`references/design-rules.md` に沿って書く：カラートークン4〜6色（HEX・用途）、書体の役割2つ以上、文字サイズの階層、余白の基準値、Signature Element（ページで記憶される1点・1つだけ）、写真のトーン。
書いたら自分で批評する：「別の会社で同じ依頼をされても同じ案にならないか」。末尾に `references/banned.md` の共通禁止＋この案件固有の禁止を5つ以上足す。

### 3. ファーストビュー3案（gpt-image-2）
`scripts/gen_image.py` で縦長（1024x1536）の **ファーストビューのデザイン画像を3案**作る。色違いではなく構造から変える：
- A：人物写真が主役（仕事中の社員・現場）
- B：文字（職種名・数字）が主役
- C：仕事の道具・現場のディテールが主役
プロンプトには OFFER.md の4点セット（誰向け／得られる変化／CTA／信頼の根拠）と DESIGN.md の色・書体を入れる。**3枚をユーザーに見せて選んでもらうまで実装しない**。

### 4. 実装（完成条件つき）
`references/structure.md` のセクション構成で `index.html` を1ファイルで書く。実装の完成条件：
1. 選んだファーストビュー案の構図・色・文字の大きさを忠実に再現する。勝手にレイアウトを変えない
2. 写真やイラストは画像として使う。無理にCSSで描かない
3. 文字はすべてHTMLのテキストで書く（画像に焼き込まない）
4. スマホ（390px）が主、PC（1280px）でも崩れない。スマホで顔と文字を重ねない
5. CTAは2〜3スクロールごと＋画面下に固定ボタン。ボタンの下に不安をほどく1行（「話を聞くだけでもOK」など）
6. 色・書体は DESIGN.md のトークン以外を使わない
7. 根拠のない実績・数字・社員の声を書かない（必要な箇所は `【要確認】`）
写真が無い場合は `scripts/gen_image.py` で作ってよいが、**架空の社員の声や顔写真を本番で実在の人物として出さない**（クライアント支給の写真に差し替える前提で、画像の下に小さく「イメージ」と入れる）。

### 5. スクショで直す
`node scripts/shot.mjs <slug>/index.html` でスマホ（390px・1画面ずつ `sp_01.png`〜、最初の1画面は `sp_fv.png`）とPC（`pc.png`）を撮り、Readで見る。**ファーストビューの1画面にCTAとその下の1行まで収まっているか**を最初に確認する。横はみ出しは WARN で出る。**一度に直すのは影響の大きい3点まで**。直したら撮り直す。最低2周。

### 6. 別エージェントで採点
サブエージェント（Agentツール・general-purpose）を新しく起動し、**実装の経緯は渡さず**、`OFFER.md`・スクショ・`index.html`・`references/rubric.md` だけ渡して採点させる。結果は `review.md`。「作り直す」に分類された項目と「このまま公開すると一番損をする箇所」だけ直す。

### 7. 納品前チェック
- CTAのリンク先がすべて本物のURLか（仮のままにしない）
- `【要確認】` が残っていないか（残すならユーザーに一覧で伝える）
- 誤字・数字の表記ゆれ
- 公開するなら Vercel（`vercel --prod`）

### 8. ルール台帳を育てる
ユーザーからダメ出しを受けたら、その場で `rules.md`（このスキルのフォルダ）に1行で追記する：`- [日付] 何をしない／何をする（理由）`。次のLPは手順1の前に必ず `rules.md` を読む。

## ファイル
- `references/hearing.md` ヒアリング項目
- `references/structure.md` 採用LPのセクション構成と各セクションの役割
- `references/design-rules.md` DESIGN.md の書き方
- `references/banned.md` 共通の禁止リスト
- `references/rubric.md` 採点基準（別エージェント用）
- `rules.md` ダメ出し台帳（使うほど育つ）
- `scripts/gen_image.py` gpt-image-2 で画像生成（`~/.zshrc` の OPENAI_API_KEY）
- `scripts/shot.mjs` スマホ・PCのスクショ（初回に playwright-core を自動で入れ、インストール済みの Google Chrome を使う）
- `examples/hado-kensetsu/` 作例（架空の建設会社）
